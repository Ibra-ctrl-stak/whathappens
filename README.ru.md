# whathappens

**Посмотрите на свой собственный запрос — байт за байтом.**

[English](README.md) | Русский

Вы десятки раз читали «что происходит, когда вводишь google.com».
`whathappens` действительно это делает: разрешает DNS начиная с корневых
серверов, открывает TCP-соединение, проходит рукопожатие TLS 1.3 и
говорит по HTTP/1.1 — а затем раскладывает *ваш* запрос в браузере на
шкалу с пояснениями. На экране — записанные DNS/TLS-байты и расшифрованное
содержимое рукопожатия и HTTP: ваши DNS-ответы, ваш ClientHello с SNI,
сертификат сервера и ответ HTTP. Без root, без Wireshark, без телеметрии.

```sh
node cli.mjs github.com/robots.txt
```

## Что он делает

1. **Итеративный DNS своими пакетами.** Без `dns.lookup`: корневой сервер → `.com` →
   авторитативный, на собственных UDP-датаграммах (RFC 1035). Потерянные и битые ответы
   не прячутся, а остаются в записи.
2. **Записывает TLS-сессию.** `tls.connect` поверх прокси-потока: шифротекст в обе стороны,
   ключи сессии из официального события `keylog`, открытый текст, который отдал Node.
3. **Расшифровывает сам.** TLS 1.3 по RFC 8446 (HKDF-Expand-Label, ключи эпох, AEAD) —
   независимо от TLS-стека Node, только криптопримитивы `node:crypto`.
4. **Разбирает поля.** ClientHello/ServerHello с расширениями (SNI, ALPN, key_share,
   supported_versions…), сертификаты (`X509Certificate`), CertificateVerify, NewSessionTicket,
   HTTP-заголовки. У разобранных событий каждый байт принадлежит одному полю-листу.
   У DNS/TCP пока нет дерева полей; внутренности X.509 показаны сводкой, без разбора DER.
5. **Самостоятельно проверяет подписи и показывает результаты.** При выборе события
   рукопожатия сервера `Certificate` или `CertificateVerify` в панели видны наши собственные
   результаты — «пройдена», «не пройдена» или «проверить невозможно» (с конкретной причиной):
   - **CertificateVerify:** подпись сервера над хэшем восстановленного транскрипта
     (ClientHello, ServerHello, EncryptedExtensions, Certificate) проверяется открытым ключом
     первого сертификата сервера; схема подписи должна соответствовать типу и кривой этого ключа.
   - **Подписи цепочки сертификатов:** подпись каждого сертификата проверяется ключом следующего
     присланного сертификата (имя издателя должно совпадать), последнего — корнем из встроенного
     хранилища Node. Это **не** полное решение о доверии: имя хоста, сроки действия, ограничения
     сертификатов (basicConstraints, keyUsage, name constraints), отзыв и Certificate
     Transparency в эту проверку не входят.

   Результаты вычислены по записанным байтам и не являются сетевыми событиями. Живое
   соединение отдельно проверяет сам Node (штатная проверка сертификата TLS); просмотрщик не
   выдаёт её за наш результат.
6. **Показывает всё на странице.** Шкала событий, hex-вид, дерево полей: клик по полю
   подсвечивает его байты, клик по байту — его поле.

## Тело HTTP

Поддерживаются chunked (размеры, данные, extensions, trailers) и gzip через встроенный zlib.
Живой запрос отправляет `Accept-Encoding: gzip`. Исходное событие `response-body` сохраняется,
а `decoded-body` содержит собранное/распакованное тело с отдельными смещениями от нуля.
При повреждении или обрыве тело помечается ошибкой, декодированное событие не создаётся.
Лимит промежуточного/распакованного буфера — 4 МиБ, число итераций chunk — 10 000.
Trailers показаны отдельно и не подменяют заголовки ответа.

Промежуточные ответы `1xx` перед финальным (например, `103 Early Hints` или `100 Continue`)
разбираются и показываются отдельными событиями `interim-response`; тела у них нет.
Разбирается не больше 16 промежуточных ответов, остальные байты помечаются ошибкой.
`101 Switching Protocols` показывается событием `protocol-switch` с пометкой «не поддерживается»,
байты после него не разбираются как HTTP. Каждый ответ сохраняет абсолютные смещения в
полученном потоке (`http/in`), а время события — время TLS-записи, доставившей его последний
байт. Если следующий ответ обрезан или повреждён, уже разобранные ответы остаются на шкале, а
оставшиеся байты становятся одним событием с пометкой «повреждено»; если поток закончился до
финального ответа, об этом сообщает пустое событие с пометкой «повреждено».

## Быстрый старт

Нужен Node.js 24+. Зависимостей нет, установка пакетов не нужна. Из папки проекта:

```sh
npm run demo                              # готовая трасса без внешних запросов
node cli.mjs github.com/robots.txt         # запрос к выбранному сайту и запуск визуализатора
node cli.mjs "https://example.com/?q=one" --timeout 60
```

Откройте напечатанный адрес `http://127.0.0.1:...` в браузере. Для остановки нажмите Ctrl+C.
Домен без схемы означает HTTPS и путь `/`. Поддержаны путь, query-параметры,
международные домены и нестандартные HTTPS-порты. Фрагмент URL не отправляется.
Ответ с редиректом отображается; автоматического перехода по нему нет.

Каждый успешный запрос сохраняет `session.json` и `keylog.txt` в новую папку `out/run-*`
относительно текущей рабочей папки. Общий таймаут DNS + TCP + TLS + HTTP — 30 секунд
(параметр `--timeout` от 1 до 300). Общий лимит сохраняемых в памяти сетевых байтов,
расшифрованных байтов и keylog — 16 МиБ. При неудачном запросе выводится ошибка;
частичная запись пока не сохраняется.

```sh
node cli.mjs --session out/run-XXXXXX/session.json   # подставьте путь к своей записи
node cli.mjs --help                                 # все параметры, включая --out
npm test                                           # локальные сокеты, без внешних запросов
```

Пакет пока не опубликован и помечен private: команда `npx whathappens` ещё недоступна.
Старые команды `node day1.mjs [путь]`, `npm run serve` и `npm run timeline` сохранены
для исходного проверочного сценария с github.com и файлом `out/session.json`.

### Сверка с Wireshark (необязательно)

С установленным Wireshark (tshark/dumpcap): запишите захват во время `node day1.mjs`, затем
`node compare-wireshark.mjs out/capture.pcapng` сравнит байт в байт DNS, оба TCP-потока,
рукопожатие и расшифровку самого Wireshark по нашему keylog. Если трафик идёт через VPN,
захватывайте интерфейс туннеля.

## TCP-сегменты из захвата (необязательно)

Node видит только чтения и записи сокета. Чтобы увидеть настоящие TCP-сегменты записанного
запроса, запишите его захват в Wireshark/dumpcap во время выполнения (при VPN — на интерфейсе
туннеля), сохраните как pcapng и откройте запись вместе с захватом:

```sh
node cli.mjs --session out/run-XXXXXX/session.json --pcap capture.pcapng
node cli.mjs --demo --pcap test/fixtures/github-robots/capture.pcapng   # готовый пример
```

- **Сопоставление:** пакеты между локальным и удалённым адресом:портом записи, в обе стороны.
  Если эту пару используют несколько соединений, одно выбирается, только когда его клиентские
  байты совпадают с записью; иначе ничего не выбирается и причина показывается.
- **Сегменты:** каждый пакет — событие `segment` (флаги, seq/ack относительно первого байта данных,
  окно, опции, длина данных), отмеченное отдельно от событий сокета. Данные привязываются к
  записанным байтам `tcp/out|in` только там, где совпадают байт в байт; иначе показываются как
  «не совпадает с записанным потоком» без байтов. SYN/ACK/FIN без данных байтов не получают.
  Учитываются переход seq через 2^32, захват с середины соединения и перекрывающиеся диапазоны.
- **Диагностика — наблюдения, а не вердикты:** пропуск значит, что байты ещё не появлялись в
  захвате (это не доказательство потери); повторно увиденный диапазон — «вероятно, ретрансмит
  (вывод)»; приход вне порядка и частичные перекрытия отмечаются. Это наши эвристики, совпадение
  с `tcp.analysis.*` Wireshark не обещается.
- **Время:** исходное время захвата каждого пакета сохраняется. Для шкалы время захвата сдвигается
  одной константой так, чтобы пакет с первым байтом ClientHello совпал с моментом, когда Node
  записал эти байты; реально пакет уходит чуть позже, дрейф часов не корректируется. Без такого
  пакета используются часы захвата как есть, и шкала прямо сообщает, что время не выровнено.
- **Ограничения читателя:** только pcapng (классический pcap отклоняется), до 64 МиБ, 500 000
  блоков, 200 000 пакетов; IPv4 + TCP поверх raw IP, Ethernet (включая VLAN) или loopback;
  IP-фрагменты не собираются и не используются; у оборванного файла сохраняются прочитанные
  пакеты. Заголовки IP/TCP пока без дерева полей.
- **Полнота по пакетам** (для любого захвата, и для `--pcap`): файл не оборван, клиентский SYN на
  месте, каждый записанный байт покрыт, соединение завершено обоими FIN с ACK на каждый либо RST.
  Недостающее перечисляется, и захват называется **неполным**. Одни пакеты никогда не делают его
  **полным**: для этого нужно знать, как шёл захват (см. `capture.json` ниже). Без этого страница
  говорит, что по пакетам замечаний нет, но как сделан захват — неизвестно.

### Захват во время живого запроса (`--capture`)

Если установлен Wireshark (dumpcap; на Windows — Npcap), whathappens может запустить захват сам:

```sh
"C:\Program Files\Wireshark\dumpcap.exe" -D          # список интерфейсов
node cli.mjs github.com/robots.txt --capture 7        # номер или имя из этого списка
node cli.mjs github.com/robots.txt --capture 7 --dumpcap "D:\Wireshark\dumpcap.exe"
```

- Интерфейс всегда выбираете вы; угадывать его программа не будет. При VPN выбирайте интерфейс
  туннеля: на физическом соединение спрятано внутри зашифрованных пакетов туннеля.
- dumpcap ищется так: `--dumpcap <путь>`, затем `PATH`, затем стандартная папка Wireshark;
  запускается без shell. Старт — после DNS (фильтру нужен адрес) и до TCP-соединения; фильтр
  `host <IPv4 сервера> and tcp port <порт>`; готовность — сообщение «Capturing on» и пауза 500 мс:
  без неё клиентский SYN пропал в 3 из 5 измеренных запусков.
- Лимиты: dumpcap сам останавливается через дедлайн запроса + 7 с (`-a duration`); захват
  обрезается на 64 МиБ (лимит читателя).
- Остановка (Windows, проверено замерами): Node не может послать dumpcap Ctrl+C, а при
  принудительном завершении dumpcap, пишущий собственный файл, теряет буферизованные пакеты.
  Поэтому dumpcap отдаёт pcapng в whathappens (`-w -`). whathappens ждёт до 2 с, пока в захвате
  появятся оба FIN (или RST) соединения, затем останавливает dumpcap и дожидается его завершения.
  dumpcap останавливается при успехе, ошибке, таймауте и Ctrl+C.
- Захват сохраняется как `capture.pcapng` рядом с `session.json` в той же папке `out/run-*`,
  вместе с `capture.json` (формат 1). В нём то, чего pcapng о себе сказать не может: интерфейс,
  причина остановки dumpcap (конец соединения, истекло ожидание, лимит размера, dumpcap завершился
  сам) и предупреждения dumpcap, а также размер и SHA-256 файла `capture.pcapng`. Путь к dumpcap,
  командная строка, идентификаторы процессов и сырой вывод dumpcap не сохраняются.
- Захват проверяется по пакетам, как описано выше, и называется **неполным** также, если dumpcap
  остановлен до конца соединения, упёрся в лимит размера или завершился раньше времени. **Полным**
  он называется, только если ни пакеты, ни dumpcap не показывают недостающего. Неудачный захват
  никогда не показывается как успешный; запись запроса всё равно сохраняется.
- Повторное открытие (`--session run/session.json --pcap run/capture.pcapng`) читает
  `capture.json` из папки захвата и снова объединяет оба уровня, поэтому предупреждения не
  теряются. Он используется, только если размер и SHA-256 совпали с открытым файлом; иначе, или
  если он не читается, он игнорируется, и страница сообщает причину. Отсутствие `capture.json`
  (старые записи, файлы Wireshark) — не ошибка.
- Ошибки объясняются: dumpcap не найден; отказано в доступе (whathappens не меняет настройки
  Npcap, адаптеров, VPN и firewall); неизвестный интерфейс; нет готовности за 10 с; ранний выход.
- Без `--capture` ничего из этого не запускается, и кроме Node ничего не нужно.

## Как проверено

- **Wireshark как независимый оракул.** Эталонная сессия совпала с захватом байт в байт
  (12/12 проверок); значения полей в `test/fixtures/github-robots/expected.json` выдал tshark,
  а не наш код.
- **RFC 8448.** HKDF, ключи и расшифровка записей — по официальным векторам, извлечённым из
  текста RFC программно.
- **Повреждённый трафик.** Испорченные, оборванные и битые записи и сообщения остаются на
  шкале событиями с пометкой «повреждено», не роняя остальное.
- **Мутационные проверки** ключевых тестов: тест должен падать на намеренно сломанном коде.

## Безопасность и этика

- Инструмент видит **только трафик, который создал сам**, и расшифровывает его ключами своих
  же сессий через официальный API Node.js. Никакого перехвата и обхода защиты.
- Живые записи (`out/`: захваты, keylog, `session.json`) исключены через `.gitignore`.
  Единственное исключение — эталонная тестовая сессия: ключи одной публичной сессии
  (`robots.txt`), см. [README фикстуры](test/fixtures/github-robots/README.md).
  TLS-тесты также содержат намеренно публичные тестовые ключ и сертификат localhost.
  Ваши живые записи содержат ключи и содержимое запроса; учитывайте это при передаче файлов.
- Локальная страница: только `127.0.0.1`, случайный порт, 256-битный токен в адресе, проверка
  `Host`/`Origin` (защита от DNS rebinding), строгий CSP без inline-скриптов, DOM только через
  `textContent`. Странице не отдаются ни keylog, ни сессия целиком.
- Текст из сети (DNS-имена, HTTP-заголовки) экранируется: управляющие символы видны как
  `\xNN` и не действуют на терминал или страницу.

## Ограничения

- Только TLS 1.3 (AES-GCM, ChaCha20-Poly1305), HTTP/1.1, IPv4 и A-записи.
- Сам слой TCP Node не видит. Реальные TCP-сегменты появляются только из захвата pcapng:
  добавленного через `--pcap` или сделанного с `--capture` (см. «TCP-сегменты из захвата»). Без
  них TCP-события — это чтения/записи сокета Node, а не сегменты.
- Готовность для `--capture` — это «Capturing on» плюс измеренная пауза, а не гарантия;
  пропущенный SYN сообщается. Пакеты, которые dumpcap ещё не передал в момент остановки
  (например, последний ACK после обоих FIN), в файл не попадут; такой захват называется неполным.
  Вживую проверено только на Windows.
- Не поддерживаются HelloRetryRequest, KeyUpdate, TLS 1.2, Brotli/deflate, цепочки transfer-coding, переход на другой протокол после `101`, несколько финальных ответов в одном соединении (pipelining), HTTP/2.
- Для живого режима нужен прямой UDP/53 к DNS-серверам; в сетях, где он заблокирован,
  используйте `--demo`. HTTP без TLS и адреса в виде IP пока не поддержаны.
- Некоторые VPN-клиенты блокируют `127.0.0.1` для браузера — тогда страница не откроется.
